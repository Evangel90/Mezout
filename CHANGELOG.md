# Changelog

## Unreleased

- Landing page redesign: full-width sections with guide lines, a hero with an animated receipt, a tabbed "How it works" walkthrough of five animations (pay any way, borrow against BTC, gasless, passkey accounts, integrations), an animated checkout, a "Safe by design" grid, a developer section with request and webhook examples, contracts and stats, an FAQ and a closing call to action. Sticky header with pill navigation and a Get started button. Animations live in `apps/web/public/motion`, generated by `docs/motion/generate.mjs`; sections ease in on scroll where supported and respect reduced motion.
- Other pages keep their column through a shared `Container`; the docs sidebar and heading anchors sit below the sticky header.
- `docs/motion`: motion graphics (SVG, MP4, GIF) for demos and slides.
- README rewritten for the buildathon submission: pitch, animated illustrations, an architecture diagram, sequence diagrams for each payment path, passkey withdrawals and WooCommerce orders, the checkout's option rules, the invoice lifecycle, a table of safety guarantees, testnet proof and tests. Setup, deployment and operations moved to `docs/DEVELOPMENT.md`.

- M4: WooCommerce gateway, `plugins/woocommerce/mezout-woocommerce` (PHP 8.1+, WooCommerce 8.5+, tested on WordPress 7.1 and WooCommerce 11.2). Classic and block checkouts; HPOS compatible. Checkout creates an invoice (idempotent per order) and returns the customer through `success_url`; only a signed `invoice.paid` with a matching amount marks the order paid; `invoice.expired` cancels unpaid orders; refunds from the order screen become Mezout refund requests, `refund.completed` notes the transfer, `refund.canceled` removes a declined refund, and refunds sent straight from the dashboard are recorded. Saving the settings checks the key and registers the webhook endpoint automatically. Adds MUSD as a store currency. Local WordPress through `@wordpress/env`; `pnpm zip` builds the installable zip; PHP unit tests for signatures and amounts.
- New webhook event `refund.canceled`, sent when a pending refund is canceled or declined.
- `checkout_url` is built from the app's canonical URL rather than the request's host.
- Dashboard MUSD transfers from a wallet set an 80,000 gas limit: Mezo testnet sometimes estimates below its own EIP-7623 minimum.

- API reference rewritten (`docs/API.md`, `/docs`): overview of a payment end to end, quickstart, authentication and key rotation, request conventions, every error code with what to do, rate limits, idempotency, pagination, object and endpoint reference, invoice status rules, a webhooks guide (receive your first webhook, handling, at-least-once delivery, timing, retries, ordering, no backfill, snapshots) and signature verification in Node, PHP and Python. Dashboard-only routes are no longer documented as public API. `/docs` has a sticky contents sidebar, labelled code blocks with Copy buttons, and a collapsible index on phones.
- `Idempotency-Key` on `POST /v1/invoices` and `POST /v1/refunds`: the first response is kept 24 hours and replayed with `Idempotent-Replayed: true`; a reused key with a different request returns `422`, one still running `409`.
- API keys are listed by prefix on the Developers tab and can be revoked (`GET /api/keys`, `DELETE /api/keys/:id`).
- Refund requests can be canceled: `POST /v1/refunds/:id/cancel`, and **Decline request** on the Payments tab. New status `canceled` and field `canceled_at` (migration `0005`).
- Invoices take `success_url`; after paying, the checkout shows a "Return to (business)" button. Payments gain `fee` and `net` (what reached the payout address).
- Rate limits are shared by every server instance (a Postgres table, migration `0005`) and `429` answers carry `Retry-After`.
- Webhook endpoint hosts are resolved when the endpoint is added, so typos and private hosts are refused straight away; each delivery is still checked.
- Invoices report `expired` one second after `expires_at`, matching the router, which accepts payment during that second; `invoice.expired` likewise waits until chain time has passed it.
- `examples/webhook-receiver`: a dependency-free Node receiver that verifies signatures, ignores duplicates and handles each event type.
- Webhooks panel explains in plain terms what a webhook is for; the delivery log shows each response.
- Site: logo and favicon, active navigation, a footer with the testnet notice and links, page titles, 404 and error pages; the checkout hides the expiry once paid.

- Business names: merchants set the name customers see at checkout (migration `0004`). A passkey account takes it from sign-up; wallet merchants are asked on the Overview tab; both can change it on the Account tab. The dashboard is titled with it.
- Checkout pass: the header shows the business name with the payout address beneath it, the order reference, and "Link expires in 23 hours"; payment options read "≈ 0.0000064 BTC · no network fee" with the signed maximum on a second line; the paid state names who received the payment.

- API reference on the website at `/docs`, rendered from `docs/API.md` at build time with an "On this page" index and GitHub-matching anchors; linked from the header, the landing page and the Developers tab.

- Dashboard redesign: sign-in is one clear choice between a passkey account and a Mezo wallet, each a separate merchant account; creating or choosing a passkey signs in straight away, and a remembered passkey signs back in with one tap. Signed in, the dashboard has Overview, Payments, Developers and Account tabs, with an account chip showing which method is in use. Payment links show a full-size QR code with Copy and Open buttons. Landing page updated for BTC and MEZO payments, webhooks and router v2.

- M3: indexer (`apps/web/src/lib/server/indexer.ts`) reads `Paid` events from both routers in chunks of up to 10,000 blocks, one block behind the head, with backfill from v1's deploy block. Invoices become paid only from indexed events. Runs from `/api/cron` (every 5 minutes through `.github/workflows/indexer.yml`), after each checkout payment (`/api/sync`), and when an unpaid invoice is read while the index is stale. New status `refunded`; invoices gain `amount_refunded` and `payment`. Migration `0003`.
- M3: signed webhooks: `invoice.paid`, `invoice.expired`, `refund.completed` and `ping`, HMAC-SHA256 `Mezout-Signature` header, retries with backoff for 24 hours, a delivery log with Retry now, up to 3 endpoints per merchant (`/v1/webhook_endpoints`). Deliveries go only to public https addresses, checked after DNS resolution and without following redirects.
- M3: refunds: `POST /v1/refunds` requests one; the dashboard sends MUSD from the payout address to the customer and Mezout verifies the transfer on-chain before marking it completed.
- M3: dashboard sign-in (signed message or passkey, 12-hour HttpOnly session); orders list with CSV export and refunds; webhooks panel; API keys minted from the session; `GET /v1/invoices` lists invoices.
- M3: `scripts/pay-invoice.mjs` creates invoices with `API_KEY` instead of `MERCHANT`; `/api/invoices` (dashboard links) needs a session.

- M2: `payWithMEZO` and `payWithBTC`: exact-output swaps on Tigris volatile pools. The router computes the least input from the pool's reserves at execution and pulls only that from the payer into the pool, so nothing needs refunding; the payer's `SwapPayment` signature binds the token, a slippage cap and a deadline. Both are gasless through BTC and MEZO permits. Router v2 deployed and verified on Sourcify; v1 still pays older links.
- M2: checkout offers Pay with BTC and Pay with MEZO with live quotes, and shows only options the connected wallet can use; Bitcoin-wallet smart accounts approve and pay directly.
- M2: payment links and invoices record their router (migration `0002`); the relayer only calls the current router or v1.
- M2: MUSD/MEZO Tigris pool created on testnet (`0x8eb88d745B0aFFF9D71AbC40d7F550Cded7bB342`, 80 MUSD + 80 MEZO); first MEZO payment `0x3c7ea6fb940eb06f93c1d276129ab94a7dec6d625efa10422918722a0cb8126a`.
- M2: production switched to router v2 (migration `0002` applied to Neon); first production MEZO payment `0x7185c981d0a3d13f182b607a4a8e322accdf1fa4b59d55cf7050c95b94b256ce`. `pnpm db:migrate:prod` migrates production through `DATABASE_URL_UNPOOLED`.
- M2: `contracts/script/seed-mezo-pool.sh` creates and funds the MUSD/MEZO Tigris pool; `scripts/pay-invoice.mjs` gains `METHOD=BTC|MEZO`.
